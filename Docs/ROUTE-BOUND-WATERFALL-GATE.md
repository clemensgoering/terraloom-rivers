# Route-bound waterfall: bounded API gate

2026-10-10, isolated `codex/route-fall-boundary` worktree. This is a **negative contract proof**, not a waterfall scene or visual acceptance. No canonical Rivers/Core/Paths or Epos product source was edited.

`Tools/RiverPlannerTests.cs` now captures one seed-42 source with a deterministic 6 m vertical step at X=0, explicit `source`, `fall` and `mouth` anchors, and `RiverRequest("main","source","mouth")`. With excavation allowed but the ordinary 0.5 maximum slope, the planner returns `NoRoute`, zero routes, and a `maximum slope` diagnostic. A replay has the same plan identity and diagnostic. Portable RiverPlanner tests: **19 passed, 0 failed**. Existing Waterfall profile/recipe tests: **24 passed, 0 failed** after building its runtime assembly; these prove the separate fall geometry recipe remains valid, not that it can be attached to a river plan. Runtime assembly build: 0 warnings/errors.

The requested positive case cannot be represented by the current public chain:

1. `RiverRequest` contains only ID/source/mouth. Neither the explicit `fall` anchor nor fall placement policy enters the request, `ProfileVersion`, or plan identity. The planner is free to route elsewhere and cannot preserve a required fall site.
2. `RiverPlanner.Field.TryEdge` samples a single terrain height at each XZ and rejects each local `drop/run > MaximumSlope`; zero horizontal run is invalid. A vertical lip-to-impact transition needs two water heights at one XZ, which `WaterfallFallSurface` explicitly supports but the current `RiverRoute.WaterPolyline`/edge search does not.
3. `RiverTerrainBrush.TryHeight` divides by horizontal `run2` and the channel/carver use one height for each XZ. A duplicated-XZ fall span cannot be passed through that path. `RiverTerrainCarver` only processes existing ordinary route spans and bounds cuts to the channel depth; it has no prepared pool, terrain-hole, replacement solid or lip/foot contact output. The existing isolated V2 waterfall prototype handles its own owned terrain/holes/solid, but is independent of a `RiverPlan`.
4. `WaterfallWaterHost.Generate` takes an independently authored `WaterfallRecipe` and caller validator, not a route-bound fall section or the river's prepared terrain. Rendering it beside a failed/independent river would falsely appear integrated.

Smallest product contract before implementation: add an optional **explicit fall intent** to a `RiverRequest` (stable fall ID and manual/seeded site selector), hash it into the request/domain identity, and return a route with typed upper reach, fall transition, pool and outlet/downstream reach under one `RiverPlan` identity. The transition must carry lip/impact/outlet anchors and a derived `WaterfallRecipe`, allowing zero horizontal fall run without relaxing ordinary reach slope. The planner must reject absent terrain clearance, either bank unsupported, insufficient pool footprint or missing downstream continuation. A prepared Rivers publication then owns and validates the matching carved terrain/holes/replacement solid and water geometry as one rollback unit; its offer/reservations must include the pool and outlet, not only the old channel strip. `WaterfallWaterHost` can supply water tessellation, but must consume that route-derived recipe and staged contact validator.

Only after this boundary exists can a Player-height lip/foot/outlet image honestly show one generated RiverRoute. No such image is emitted here. Existing standalone waterfall imagery and the R3 River+Ground-Path image remain separate evidence and do not close this gate.
