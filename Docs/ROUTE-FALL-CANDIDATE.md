# Opt-in route fall candidate, no publication

2026-10-10, isolated branch `codex/route-fall-boundary`. This contract step extends `RiverRequest` with optional `RiverFallSite(id, anchorId)`; Unity `RiverConnectionSettings` exposes the paired fields. A request without a fall retains its previous profile/domain hash bytes and ordinary `RiverPlanner` route/slope behavior. A fall request hashes both stable identifiers into the domain identity and invokes a separate, read-only candidate inspection. A seed-derived anchor and a manually authored anchor use the same captured Core snapshot; the candidate stores that exact `PlanIdentity`.

`RiverFallCandidate` records the typed source/upper reach, lip, impact, compact pool, outlet and lower end plus a derived `WaterfallRecipe`. The 6 m test has **identical lip/impact XZ and distinct Y**. Ordinary reaches are still checked against unchanged `MaximumSlope`; only the explicit candidate represents the vertical transition. Its profile requires excavation permission. The bounded straight-site inspection rejects unsupported upper/lower banks, absent or hard-reserved pool/outlet footprint, insufficient lower reach and stale Core identity. It uses the source height sampler without terrain writes. This is a local transition candidate, not a final searched/detoured RiverRoute or proof that a Unity heightfield can contain the cliff.

Publication is deliberately gated: `RiverOutcome.FallCandidateOnly`, `RiverPlan.Complete == false`, zero `RiverRoute` entries for the fall request, `ToContribution` throws, and `TerraLoomRivers.PrepareFromSnapshot`/`Generate` cannot publish it. A mixed batch containing a fall candidate is likewise incomplete. `WaterfallWaterHost` remains detached; no Player water image is claimed.

Portable `RiverPlannerTests` 21/21, including deterministic candidate replay, distinct fall-vs-legacy fingerprint and negative bank/pool/short-lower/stale cases. `RuntimeCompile` 0 warnings/errors. Native Unity 6000.3.9f1 batch compilation exit 0, `TerraLoom.Rivers.Runtime` recompiled with no C# errors. Evidence: `Docs/Evidence/route-fall-candidate-portable.txt` and isolated `.artifacts/RouteFallCompileFinal.log`.

The smallest next terrain/publication step is a prepared **fall earthworks/contact output** keyed by `RiverFallCandidate.CoreInputIdentity` and site ID. It must stage an owned terrain cut plus required terrain hole/replacement solid at the vertical face, compact pool floor/sides, full-width bank bearings and matched upper/lower channel contacts. It must validate actual staged terrain and water meshes at lip, impact, pool, sill and downstream seam, including negative insufficient support/space cases. Only then may `RiverPlan` gain a complete route/contribution and `PreparedPublication` atomically swap terrain, collider, fall solids, water and ordinary reaches. Do not reinterpret the fall as an ordinary `RiverTerrainBrush` span: it divides by horizontal run squared and cannot represent repeated XZ with different Y.
