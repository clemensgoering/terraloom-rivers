# Gate6f: shared boundary fall, bridge and Player evidence

The shared Core+Rivers+Paths boundary-fall fixture now bakes a scene and all owned terrain, material and mesh assets, reopens that scene in a separate Unity 6000.3.9f1 process, and builds/runs a Windows Development Player. The fixture is generated by `BoundaryFallCompositionTests` with `-terraloomBakeBoundary`; the separate `ReopenedBoundaryFallBridgeRetainsOwnedAssetsAndConstruction` test uses `-terraloomReopenBoundary`. The saved scene is `Assets/TerraLoom/Integration/Generated/TerraLoomBoundaryFallBridge.unity` in the canonical Integration project. Source and carved TerrainData, TerrainCollider binding, format-4 river JSON, path JSON, five river meshes, timber-truss structure mesh/collider and two ramps survive reopening. The composition's `ValidateCurrent` passes. Reports: `Integration/Temp/BoundaryFallBakePlayer.xml` 1/1 and `Integration/Temp/BoundaryFallReopenPlayer.xml` 1/1.

Do not call standalone `Rivers.LoadPlanJson` or `Paths.LoadPlanJson` to validate a Composition publication: those APIs recapture each module's own input. Composition deliberately includes the other module's protected reservations in its shared snapshot, so the standalone fingerprint differs from the stored shared plan even when the bake is intact. Use the Composition's `ValidateCurrent` for the shared saved scene; a future selective-reload API must preserve its joint snapshot and authority.

`BoundaryFallPlayerBuilder.BuildBatch` builds `.artifacts/BoundaryFallBridgePlayer/TerraLoom.exe`. The opt-in Player probe runs with `-terraloomBoundaryProbe -terraloomBoundaryOutput <directory>`, exits 0 and records `TERRALOOM_BOUNDARY_PLAYER_PASS` in `Integration/.artifacts/BoundaryFallBridgePlayer/PlayerFinal.log`. It confirms the terrain/collider binding, five river pieces, one timber structure collider, two ramps, three supporting raycasts, three CharacterController landings, and 61 continuous CharacterController steps over the 8.00 m deck plus approaches. Ten fixed 960x540 images are in `Integration/.artifacts/BoundaryFallBridgePlayer/images/`: the five Gate6c camera names (`lip`, `side`, `foot`, `pool`, `outlet`) plus `fall-wide`, `receiving-bank`, `bridge-end`, `bridge-underside`, `overview`. The first walking attempt was blocked by an earlier probe controller at the same location; those temporary controllers were still alive until end-of-frame. Running the continuous bridge probe before those independent landings removed the test-harness interference; the final Player run passes.

**Visual V0 still fails.** The images show a sheer planar rock wall, straight vertical seams and a hard foot/shoulder transition; the receiving banks remain simplified and the river reads as a flat strip. These are generator geometry/terrain-shaping issues. The test intentionally uses plain URP Lit materials, so overexposed white terrain/water/bridge and absent vegetation/textures are fixture/material limitations, not evidence that production shading is correct. The bridge geometry is visibly present and supported, but buyer-grade visual parity with `0_Game` has not been established. The initial five camera poses also become partly obstructed by the new bridge or cliff; the supplementary views expose the geometry better. No Epos product files were changed.

The portable RiverPlanner suite (23/23), Rivers physical-publication tests (2/2), shared Composition transaction suite (23/23), and focused positive/negative bridge EditMode test (1/1) passed before this bake/Player gate. Generated scene/Player evidence is local to the canonical Integration project; tracked fixture/test/probe/builder source lives under `Rivers/IntegrationProject/Assets/TerraLoom/Integration/` and was copied into that project for these runs.
